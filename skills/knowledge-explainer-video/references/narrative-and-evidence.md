# 叙事与证据

## 先判断资料属于哪种结构

### 项目演进或版本迭代

优先采用循环：

```text
当前能力 → 解决的实际问题 → 尚未解决或新出现的痛点
→ 下一次迭代 → 怎样验证 → 新的边界
```

每轮必须说明用户价值，不把提交文件数、代码量或版本号本身当成果。

### 概念、方法或流程

采用：为什么重要 → 旧认知或问题 → 核心机制 → 分步说明 → 示例 → 限制 → 可执行结论。

### 对比与选择

采用：共同问题 → 比较维度 → 关键差异 → 适用场景 → 取舍 → 推荐结论。

## 证据表

每个事实保存稳定 `evidenceId`，包含来源路径或 URL、原文位置、可支持的观点和限制。区分：

- `fact`：资料直接支持；
- `interpretation`：基于资料的合理解释；
- `claim-needs-confirmation`：资料不足；
- `visual-only`：只用于说明，不承担事实证明。

正式讲稿中的事实句必须引用至少一个 `evidenceId`。无法证明时删除、降级为假设或向用户确认。

## 讲稿规则

- 先找到目标观众熟悉的具体情境，以及可以感受到的失败、困惑或效率问题；一句只承担一个主要动作、判断或结论；
- 技术名词先通过画面中的用途和结果解释，再补必要术语；不连续堆砌命令、版本号或实现细节；
- 每章末尾留下由当前能力尚未解决的问题，自然引出下一章；
- 结尾把能力变化收束成路径，不重复罗列章节；
- 为每句保存 `narrationId`、`text`、`purpose`、`evidenceIds`、`targetDurationSec`；
- 内容确认后建立“旁白句 → 知识点 → 人物或物件动作 → 可见结果 → 所需素材”映射。抽象概念至少有一次可观察的变化：例如分支显示主路和试验路线，冲突显示双方修改、暂停、选择和结果；
- 人工录音后补充 `startSec` 和 `endSec`，它们才是正式画面时间。字幕还需根据实际语音另行分段，不能直接把整句讲稿当字幕。

## 信息密度检查

如果一句必须快速朗读才能放入目标时长，优先删减次要细节或延长视频。90–180 秒仅供初估，不是上限；时长服从理解负担与正式录音。讲稿更改后重新检查受影响的场景、动作、字幕和转场，不沿用过期时间戳。
