# 叙事与证据

## 先判断资料属于哪种结构

### 项目演进或版本迭代

优先采用循环：

```text
当前能力 → 解决的实际问题 → 尚未解决或新出现的痛点
→ 下一次迭代 → 怎样验证 → 新的边界
```

每轮必须说明用户价值，不把提交文件数、代码量或版本号本身当成果。

### 概念、方法或流程

采用：为什么重要 → 旧认知或问题 → 核心机制 → 分步说明 → 示例 → 限制 → 可执行结论。

### 对比与选择

采用：共同问题 → 比较维度 → 关键差异 → 适用场景 → 取舍 → 推荐结论。

## 证据表

每个事实保存稳定 `evidenceId`，包含来源路径或 URL、原文位置、可支持的观点和限制。区分：

- `fact`：资料直接支持；
- `interpretation`：基于资料的合理解释；
- `claim-needs-confirmation`：资料不足；
- `visual-only`：只用于说明，不承担事实证明。

正式讲稿中的事实句必须引用至少一个 `evidenceId`。无法证明时删除、降级为假设或向用户确认。

## 讲稿规则

- 一句只承担一个主要动作、判断或结论；
- 先讲人能感受到的问题，再讲实现；
- 技术只解释“为什么这次能解决”，不连续堆砌术语；
- 每章末尾留下一个自然问题，引出下一章；
- 结尾把能力变化收束成路径，不重复罗列章节；
- 为每句保存 `narrationId`、`text`、`purpose`、`evidenceIds`、`targetDurationSec`；
- 人工录音后补充 `startSec` 和 `endSec`，它们才是正式字幕与画面时间。

## 信息密度检查

如果一句必须快速朗读才能放入目标时长，优先删减次要细节或延长视频。知识讲解不以固定 90 秒为硬目标；默认允许 90–180 秒自适应。
